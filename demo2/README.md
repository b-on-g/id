# $bog_id

Единый вход на Гипер Базе. Приложение не получает ключ пользователя: оно показывает свой Pass, а Гипер ID выдаёт ему права на отдельный ленд.

## Поток

1. Приложение генерирует свой ключ, как обычно: `$giper_baza_auth.current()`.
2. `$bog_id_login( provider, pass, scope )` открывает попап Гипер ID.
3. Попап шлёт `{ bog_id: 'ready' }` открывшему окну, получает `{ bog_id: 'request', pass, scope }`. Приложение определяется по `event.origin`, а на общем с провайдером origin по папке открывшей страницы.
4. Пользователь разрешает. На пару «приложение + scope» Гипер ID заводит два зашифрованных ленда: указатель и данные. Pass получает `read` на указатель и `post` на данные.
5. Приложение получает `{ lord, name, pointer }` и находит ленд данных через `$bog_id_land( pointer )`.

Тот же сайт с другого устройства приходит с другим Pass и получает права на тот же ленд.

## Отзыв и ротация

Отзыв устройства или всего приложения делает `fork()` ленда данных. Новый ленд подмешивает старые данные через `Tine`, но зашифрован новым секретом. Оставшиеся Pass получают `post` на новый ленд, отозванные получают `deny` на указатель и на все прежние ленды. Указатель переводится на новый ленд, поэтому приложения ссылку не меняют.

## Профиль и passkey

Профиль лежит в home-ленде под своим ключом `bog_id` (корень home занят другими приложениями, Gram стирает там `Name`). Он открыт: приложение читает имя живьём через `$bog_id_profile_of( lord )`.

Passkey с расширением PRF хранит лорд в `user.id`. Его секретом шифруется корневой ключ, и шифровки лежат в home-ленде (`Vault`, до пяти через пробел, по одной на привязку). На новом устройстве «Войти по passkey» достаёт лорд из `userHandle`, ждёт шифровку из Базы, расшифровывает ключ и перезагружает страницу.

## Несколько аккаунтов

Ключи аккаунтов лежат в `localStorage` под `$bog_id_account`. Переключение меняет текущий ключ и перезагружает страницу. После выхода остаются имя и шифровка ключа, поэтому вернуться на том же устройстве можно по биометрии без связи с Базой.

## Для других фреймворков

`$bog_id_login` зависит только от DOM. Для своего Pass и чтения ленда нужна Гипер База из npm.

```js
const { lord, name, pointer } = await $bog_id_login( 'https://b-on-g.github.io/id/', pass, 'notes' )
const land = $bog_id_land( pointer )
```

## Модули

- `bog/id` схема: `$bog_id_grant`, `$bog_id_store`, `$bog_id_profile`
- `bog/id/login` функция входа для приложения
- `bog/id/land` указатель → ленд данных
- `bog/id/key` один ключ приложения на все устройства
- `bog/id/profile` публичный профиль лорда
- `bog/id/vault` шифрование корневого ключа секретом passkey
- `bog/id/account` аккаунты этого устройства
- `bog/id/row` строка аккаунта или действия
- `bog/id/yard` мастер Базы: первый, кто ответил за 4 секунды, по порядку из сида
- `bog/id/path` ключ Базы по папке страницы, а не по origin
- `bog/id/app` провайдер: согласие, профиль, passkey, подключённые приложения, отзыв
- `bog/id/demo` приложение с заметкой в выданном ленде
- `bog/id/demo2` то же со своим ключом через `bog/id/path`

## Свой ключ на общем origin

Подключить `include \/bog/id/path` в `meta.tree` приложения. Ключ ляжет в `localStorage` под `$giper_baza_auth:<папка страницы>`. В корне домена остаётся обычный `$giper_baza_auth`.

## Один ключ приложения на всех устройствах

`$bog_id_key( pointer, own )` хранит ключ приложения в выданном ленде: первое устройство кладёт свой, остальные получают его и ставят через `$giper_baza_auth.current( auth )`. Пока ленд не догнал мастера, возвращает пустую строку. Отзыв не отбирает уже полученный ключ: он закрывает только ленд.
